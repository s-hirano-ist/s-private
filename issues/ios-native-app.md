# iOSネイティブアプリ実装計画

## 実装進捗

- [x] 第1段階: Xcode 27／iOS 27 Simulator向けの開発環境、XcodeGenによるプロジェクト生成、SwiftUIサンプルアプリ、単体／UIテスト、GitHub Actionsを整備する。
- [ ] 第2段階以降: 実機署名、Share Extension、App Group、Auth0コールバック、モバイルAPI、各ドメイン機能、オフライン同期を実装する。

第1段階ではWeb／React UIを変更せず、Apple標準のSwiftUI部品だけを使用する。リポジトリ規約が要求するStorybook MCPは作業セッションで利用できなかったため、追加指示は取得していない。

## 成果物と確定要件

本issueはiOSネイティブアプリの実装計画と段階的な進捗を記録する。issue追加時点では計画のみを記録し、実装は上記の進捗単位で後続PRとして対応する。

- 個人用・iPhone専用。最低対応OSはiOS 27。
- Swift＋SwiftUIを採用し、同じリポジトリの `ios/` に配置する。
- Next.jsを引き続きWebアプリ兼サーバーとして使用する。
- WebViewによるアプリ埋め込みを禁止し、本文・フォーム・画像ビューアもネイティブで実装する。
- 4ドメインの主要機能、Share Extension、新規登録のオフライン対応を含める。
- Apple Intelligence、Siri、App Intentsの機能実装は対象外。後から追加しやすい構造にする。
- 無料のPersonal Teamを使い、Xcodeから実機へインストールする。TestFlight・App Store公開は対象外。

## 対応機能と画面

| 対象 | 初回の対応内容 |
|---|---|
| 記事 | 一覧・状態別表示・カテゴリ選択・登録・削除・外部記事をSafariで開く |
| ノート | 一覧・Markdown本文表示・登録・削除 |
| 画像 | 一覧・拡大表示・写真／ファイルからの登録・削除 |
| 書籍 | 一覧・詳細・Markdown本文・書影・ISBN／評価／タグを含む登録・削除 |
| 検索 | 既存のサーバー検索による記事・ノート・書籍の横断検索 |
| 同期管理 | 保存待ち・送信中・要修正・認証待ちの表示、再送・未送信データの取り消し |
| 設定 | 認証状態・ログアウト・キャッシュ削除・接続先情報 |

既存Webにない編集機能、画像検索、エクスポート処理のモバイル移植は追加しない。既存の状態遷移と登録ルールを維持する。

- 標準のTabView、NavigationStack、List、Form、sheet、toolbarを使用する。4ドメインと検索を主な導線にする。
- Liquid Glassはシステム標準のバー・操作部品への適用を基本とし、本文全体に独自のガラス装飾を敷かない。[Appleの採用ガイド](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)
- Dynamic Type、VoiceOver、ダークモード、透明度・動きの軽減、日本語／英語に対応する。
- MarkdownはSwiftで解析し、見出し・リスト・表・コード・リンク・画像をネイティブ表示する。HTMLは実行しない。
- Apple Intelligenceの将来導入に備え、取得・検索・登録操作と画面遷移をViewから分離する。今回、AI用の空実装や専用APIは作らない。

## サーバー・API・認証

### 既存処理の共有

既存のapplication-servicesは、分離済みの `.core.ts` にもCookie認証、FormData、Web向けエラー処理が残っている。これらをHTTPの入口から独立したユースケースへ整理する。

- ユースケースの入力を、検証済みコマンドと認証済みユーザー情報に統一する。
- WebのServer ActionsとiOS用Route Handlersを、同じユースケースを呼ぶアダプターにする。
- DB、ドメインルール、画像検証、MinIO、検索、イベント処理は既存のTypeScript側で共有する。
- React表示用DTOから、本文・ID・日時・状態を保持するAPI用DTOを分離する。
- リポジトリ内の`updateTag`依存を整理し、APIからの更新でもWeb側キャッシュを適切に無効化する。
- 「全mutationはServer Actions」の既存規約に、認証済みネイティブAPIの例外を設け、実装時にアーキテクチャ文書と規約の正本を更新する。

### API契約

Next.jsに `/api/mobile/v1` を設ける。

- 4ドメインの一覧・詳細・登録・削除、カテゴリ一覧、横断検索、認証済みメディア取得を提供する。
- 一覧はページングと既存の状態フィルタに対応する。
- OpenAPIを契約として保存し、SwiftのCodableモデルと契約テストを対応させる。
- 日時はISO 8601、識別子は文字列とし、検索結果にはネイティブ画面を開ける型付きの参照を返す。
- エラーはHTTPステータスと安定したエラーコードで返す。HTMLへの認証リダイレクトや日本語メッセージ文字列への依存を避ける。
- 登録には端末生成の操作IDを必須とし、同一操作の再送で二重登録しない。

画像・書影は既存の10 MiB上限を維持する。HTTP基盤のリクエストサイズ上限を避けるため、1 MiB単位の認証付き分割アップロードと完了APIを設け、MinIOの一時領域に保存する。完了時にサイズ・実体形式・所有者を検証して既存処理へ渡す。未完了データには期限と削除処理を設ける。

HEIC等はiOS側でJPEGへ変換し、向きを補正する。変換後にもサイズ上限を検証する。

### 認証・所有者の対応付け

- Auth0にNative ApplicationとAPI audienceを追加する。
- Auth0.swiftとシステム認証セッションでAuthorization Code＋PKCEを使用する。ログイン用のシステムブラウザーはアプリ画面のWebView化に含めない。[Auth0公式ガイド](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow-with-pkce/add-login-using-the-authorization-code-flow-with-pkce)
- 無料署名を前提にカスタムURL schemeでコールバックを受け、資格情報をKeychainに保存する。クライアントシークレットは配布しない。
- APIはアクセストークンの署名・issuer・audience・期限を検証する。
- Auth0のsubjectを既存Better AuthのAccountと照合し、既存のUser IDへ解決する。メール一致での自動統合や、新しい別ユーザーの自動作成はしない。
- 現行AccountのissuerはAuth0 issuerと一致するとは限らないため、設定済みプロバイダーとaccountIdの対応を明示して解決する。
- 個人用APIは設定された所有者だけを許可する。検索が現在ユーザー別に分離されていない点も、この認可で保護する。
- データ・画像の取得と変更には既存のtenant contextを適用し、クライアント指定のuserIdを信用しない。

## オフライン保存とShare Extension

### 端末側

SwiftDataに取得済みデータと登録キューを保持し、添付ファイルはアプリ管理領域に保存する。サーバーを登録済みデータの正本とする。

- オフラインでは、取得済み本文・ダウンロード済み画像の閲覧と4ドメインの新規登録を可能にする。
- サーバー検索・登録済みデータの削除はオンライン限定とする。
- 初回ログインはオンライン必須。その後の未送信データはユーザーに紐付ける。
- 起動・フォアグラウンド復帰・手動操作で同期する。アプリ終了中の自動送信は保証しない。
- 通信失敗は再試行し、認証失敗はログイン待ち、入力不備・重複は修正待ちにする。無限再試行しない。
- 送信後に応答を受け取れなくても同じ操作IDで再送する。送信中の内容は変更せず、確定した失敗を修正するときは新しい操作IDを発行する。
- 未送信データはキャッシュ削除の対象外にする。ログアウト時は未送信件数を示し、同期するか破棄するか選べるようにする。
- 再取得時に既知の削除をローカルへ反映し、未更新のキャッシュには取得日時を表示する。全件同期やCloudKit同期は行わない。

### サーバー側の再送保証

操作ID・所有者・入力ハッシュ・処理状態・結果を保存する。

- 同じ操作ID・同じ入力には以前の結果を返す。異なる入力での再利用は拒否する。
- 業務データの作成と成功記録を同一DBトランザクションで確定する。
- ストレージ処理は操作IDに対応した保存先で再実行可能にし、DB確定後の通知・キャッシュ更新失敗を登録失敗として扱わない。
- 再送による通知の重複や処理漏れを防ぐため、副作用は永続的な処理記録から再開できるようにする。

### Share Extension

- URLは記事、テキストはノート、画像は画像登録として受け取り、保存前に確認・必須項目入力を行う。
- 書籍登録は本体アプリで行う。
- ExtensionはApp Group内の受け取り領域へ操作ID・入力・添付を原子的に保存する。本体が起動時にSwiftDataのキューへ取り込む。
- Extension自身は認証トークンを保持せず、サーバー送信もしない。
- 保存完了表示は端末への書き込み成功後に出し、「アプリを開くと同期」を明示する。
- 二重取り込み、共有途中の終了、ディスク不足、複数画像、未ログイン時を処理する。未ログイン時の共有は本体での初回ログインへ案内する。

現在のApple公式対応表ではApp Groupsは無料のApple Developerにも対応している。実装開始時にPersonal Teamで本体・Extensionの署名と共有領域へのアクセスを実機検証する。[対応表](https://developer.apple.com/help/account/reference/supported-capabilities-ios)

## 実装順序・検証・完了条件

1. **実機成立性を確認**：iOS 27対応Xcode、無料署名、Share Extension、App Group、Auth0コールバックを最小構成で検証する。成立しない場合は有料化や機能削減を自動決定せず、ユーザーへ確認する。
2. **共有ユースケース・APIを整備**：認証、所有者解決、DTO、キャッシュ更新を実装し、Web側の回帰を確認する。
3. **オンライン版を完成**：4ドメインの主要機能と検索、ネイティブビューアを実装する。
4. **永続化・再送保証を追加**：登録キュー、画像分割送信、サーバーの冪等性、取得済みデータ閲覧を実装する。
5. **Share Extensionと運用を完成**：共有保存、取り込み、アクセシビリティ、実機導入・再署名手順を整備する。

受け入れ条件：

- [ ] WebとiOSが同じ所有者・同じデータを扱い、相互の登録・削除が再取得後に反映される。
- [ ] 不正／期限切れトークン、別所有者、他人のID・画像・操作IDへのアクセスを拒否する。
- [ ] オフライン登録後の再起動・通信切断・応答欠落・重複送信でも、登録が失われず二重作成されない。
- [ ] Safari／写真からの共有を機内モードで保存し、本体起動後に同期できる。
- [ ] Markdown・画像・入力・ナビゲーションにWebViewを使用しない。
- [ ] AIが利用できない端末でも今回の全機能が動作する。
- [ ] Swift Testing／XCTest、XCUITest、iOS 27実機で検証する。サーバー変更には`pnpm check:agent`と`pnpm build`、DB変更にはPrismaの差分・適用検証、既存Webには主要フローのE2Eを実施する。
- [ ] 将来の実装時は、UI着手前にリポジトリ規約のStorybook MCP指示を取得する。計画時の調査では該当ツールは利用できていない。
- [ ] 無料署名の7日間の期限と、データを消さずに再署名する手順を記載する。[Appleのアカウント制限](https://developer.apple.com/help/account/basics/about-your-developer-account)
